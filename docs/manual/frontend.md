# Frontend Module Manual

## Overview

The Frontend Module is a custom web server used by Sunspots to handle incoming client requests and serves stored data generated by other modules.
The module includes extra features inspired by Apache to allow for the hosting of web interfaces through automatic file searching and more.

## Architecture
The Frontend Module implements a thread-pool server architecture. One main thread is responsible for accepting incoming connections and adding them to a circular client queue, worker threads then process clients from the queue by reading their HTTP requests and serving responses. This design prevents blocking on slow clients and allows multiple requests to be processed concurrently.

## Supported Features
The Frontend Module currently supports a limited set of HTTP functions:
- Methods: GET, OPTIONS
- Keep-Alive connections
- Static file serving
- Alias based routing
- Hardcoded endpoints
- Basic MIME type detection
- Index file resolution for directories

The module currently does not support:
- POST request bodies
- Chunked transfer encoding
- Range requests
- HTTPS
- Compression

## The Configuration
Below is a model of the expected configuration for the Frontend Module:
```json
{
    "name": "Frontend",
    "bin_path": "./build/debug/src/frontend/sunspots_frontend",
    "Timer-type": 0,
    "heartbeat_interval": 4,
    "server_threads": 8,
    "server_port_http": 10480,
    "server_port_https": null,
    "server_listen_queue": 16,
    "client_queue_size": 32,
    "allow_file_search": true,
    "file_search_dir": "./",
    "aliases": [
        {
            "target_url": "/README",
            "target_file": "./README.md"
        }
    ]
}
```
Some values belong to the Sunspots daemon, this manual will only cover what is custom to the Frontend Module:
- `server_threads`: Controls how many worker threads to create that handle connecting clients in the client queue.
- `server_port_http`: Controls what port to host the HTTP server on.
- `server_port_https`: Intended to control what port to host the HTTPS server on, currently null as a HTTPS server has not been developed.
- `server_listen_queue`: Specifies how many clients can be queued in the socket listener created by listen().
- `client_queue_size`: Controls how large the circular client queue should be, recommended to leave higher than the listen queue to avoid potentially dropping connections.
- `allow_file_search`: Enables treating the requested URL as a file path to load if no endpoint matches the request.
- `file_search_dir`: What folder to search for a file in using the URL as a relative path.

## Handling Requests
The program's main code is written in [src/frontend/frontend_main.c](src/frontend/frontend_main.c) and uses functions from [src/frontend/http_main.c](src/frontend/http_main.c) to maintain a constant loop of accepting connecting clients.

Upon creation of the HTTP server, several workers (amount controlled by the `server_threads` config) are created which run code from [src/frontend/http_worker.c](src/frontend/http_worker.c). Incoming client connections are accepted by the main thread and then written to a circular buffer that each worker waits for which is defined in [src/frontend/client_queue.c](src/frontend/client_queue.c).

### Request Flow
1. Client connects to the HTTP server socket
2. Main thread accepts the connection, placing it in the circular client queue
3. A worker thread retrieves the client ID from the queue
4. Worker reads & parses the HTTP request into a struct
5. Struct is processed by the request handler which generates a response
6. Response is returned by the worker thread
7. If keep-alive is requested, go to number 4, otherwise continue
8. Connection is closed

## The Workers
When a worker receives a client to handle, it begins reading data from the socket, upon reaching the end of header info the request is converted to a struct using the HTTP parser in [src/frontend/http_parser.c](src/frontend/http_parser.c). This parser is a restored version from our previous work with all memory leaks caused by malformed requests removed. After a request successfully parsed and forwarded to [The Request Handler](#the-request-handler), if the client has not disconnected and explicitly requests a keep-alive connection the thread will continue reading from the client in anticipation of another request. The socket has a strict timeout to prevent permanently locking a thread to one client so that other requests can be processed.

## The Request Handler
After a request is parsed and validated by a worker, it's submitted to [src/frontend/endpoints.c](src/frontend/endpoints.c) where three variants of URL handling take place which will be described in this manual.

### Hardcoded Endpoints
These endpoints are created by the developer directly in the [src/frontend/endpoints.c](src/frontend/endpoints.c) file. In it you can run a direct string comparison between the requested URL to determine what to do. Because these endpoints are implemented directly in code, they allow the developer to implement arbitrary behavior such as dynamic responses or communication with other modules.

### Aliases
Aliases are defined in the module's configuration set, each alias contains a target URL and a target file path. If the request URL matches a defined alias, the module tries to read the file at the target path and directly return the content to the requester. This feature exists as a controlled override for [File Searching](#file-searching) and can be used to:
- Expose files outside the normal file search directory
- Create cleaner or shorter URLs for commonly accessed files
- Provide stable endpoint names even if file locations change

### File Searching
File Searching is controlled in the module's configuration set under `allow_file_search` and `file_search_dir`. If file searching is allowed and no hardcoded/alias URL matched the request, the module will attempt to treat the URL as a file path and search inside of `file_search_dir` as if it's the working directory

Before searching the URL is sanitized to ensure directory traversal to break out of the file search directory cannot be performed. If the request URL asks for a folder, the module will attempt to mimic Apache behavior and search for a file named "index" matching common file types like html, txt, json and so on. If a matching file is found it gets returned, otherwise the module returns a 404.

## Security Considerations
- When URLs are treated as file paths they are sanitized to prevent directory traversal that escapes the file search directory.
- The server only serves files from controlled directories or explicitly configured alias paths.
- Files can not be executed, the module only loads its contents to return to the requester.
- Currently only GET and OPTIONS are supported. OPTIONS exists to avoid issues with frontend pages but any other request type is treated as GET.
- Keep-alive is supported but has a strict timeout so clients that do nothing don't deadlock a worker thread.

## Performance Considerations
- The module uses a thread pool instead of one thread per connection to avoid overwhelming the system with excessive thread creation under high connection load.
- Keep-alive is supported to allow for fast multi requests without needing to close & reopen a connection for each request.
- The Frontend Module was not designed with large files in mind.
  - Files requested are not cached after being handled.
  - Files are fully loaded into RAM before being used to generate a response body, requiring double the file size in available memory to allocate.

## Future Improvements
If this module were to be rebuilt for public use covering a wide range of use cases, possible improvements would be:
- File caching
- Chunked transfer encoding
- Range requests
- Rate limiting
- Less RAM usage from loaded files

## Drawbacks
Given that the initial intended use case for the module was to serve tiny JSON files, although the featureset was extended the module isn't particularly memory efficient. Successfully returning a response for a file requires twice the file size in available memory to allocate and there is no cache layer for previously loaded files, if large files are hosted then repeated requests to it can overwhelm the target disk.
